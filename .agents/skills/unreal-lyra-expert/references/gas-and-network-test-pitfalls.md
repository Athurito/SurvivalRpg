# GAS and network test pitfalls

Behavior observed in this project's automation tests and PIE sessions on UE 5.8. Read it before writing tests that step timers or standalone test worlds, before server code that adds or executes GameplayCues, and before PIE network tests. Correct this file in the same PR when a finding no longer holds.

## Timers in test worlds

- `FTimerManager::Tick` fires a timer only when the time is strictly past its expire time. Stepping exactly onto a deadline, such as `AdvanceTimers(0.5f)` for a 0.5 s timer, fires it one step late, and a looping timer may then fire twice. Step slightly past each deadline (0.55, then 0.5 each), as the harvesting tests do.
- `FTimerManager::Tick` runs once per `GFrameCounter`; a second tick in the same frame does nothing. Guard the counter with `TGuardValue<uint64> FrameGuard(GFrameCounter, GFrameCounter)` and increment it before each tick.
- A timer set outside a tick is pending: it gets its expire time only at the end of the next tick, so that tick's delta does not count toward it. Tick once with 0 before advancing time. After that tick, and after every `AdvanceTimers`, a timer set in the same `GFrameCounter` frame is active at once (`HasBeenTickedThisFrame`), so `AdvanceTimers(2.5f)` then `AdvanceTimers(0.6f)` fires a 3 s timer set after `PrimeTimerManager` (HRW-04).

## Standalone test worlds

- `FScopedTestWorld` (`InitializeStandalone`) never initializes its actors, so `AActor::RouteEndPlay` skips them: unloading a level instance or destroying an actor calls no `EndPlay`. Call `World->InitializeActorsForPlay(FURL())` before spawning when a test needs it. `ULevelStreamingDynamic::LoadLevelInstance(World, "/Engine/Maps/Entry", ...)` plus `FlushLevelStreaming(Full)` gives a real runtime level instance.
- Such worlds run as `NM_Standalone`, so Server and Client RPCs on a spawned PlayerState execute at once on the calling machine. A test can check a server request and its owner-only client reply, such as `ClientReportRejectedRequest`, synchronously; a PIE network test must prove the round trip (MST-04).
- A cross-inventory transfer rebuilds the moved items, and the subtree of a container item, as new instances in the target inventory under the same `ItemId`s. Re-resolve them with `FindItemById` instead of keeping the source pointers (MST-05).
- Components registered there never run `BeginPlay`, so a base-storage component keeps 0 shared Materials capacity points instead of its `BaseMaterialCapacityPoints`. Seed the pool with `AddMaterialCapacityPoints` and create rows with `StoreDefinitionResource`. `AddResourceCapacity` is the legacy per-definition seam and silently does nothing in the required shared-capacity mode; two view model tests kept calling it after shared capacity became the default and failed unnoticed.
- In such worlds `AActor::IsNetStartupActor()` is true for every spawned actor. To model a runtime-spawned actor, clear both `bNetStartup` and `bNetLoadOnClient`.
- An ability still running when the test world is destroyed gets cancelled during cleanup, after game-instance subsystems such as the GameplayMessageSubsystem are gone. Skip delivery when `World->bIsTearingDown || World->IsBeingCleanedUp()`.
- A UMG widget creates its MVVM view and runs `OnInitialized` only with a valid player context, unless its class sets `bCanCallInitializedWithoutPlayerContext`. Create `NewObject<ULocalPlayer>(GEngine)`, spawn an `APlayerController`, set `PC->Player` and `LocalPlayer->PlayerController`, call `World->AddController(PC)` (spawned actors never run `PostInitializeComponents` there, so the controller is not in the list), then `CreateWidget(PC, Class)`.
- `ARpgCharacter::OnAbilitySystemInitialized` refills health to max on authority. Compare against the attributes after `InitializeAbilitySystemComponent`, not the spawn values.
- A default `FHitResult` has `Item` 0, not `INDEX_NONE`. Synthetic hits that a test builds by hand therefore name instance 0; compare or exclude them by that item, not by `INDEX_NONE` (MST-09b).
  - Real line traces, sweeps and overlaps on a single-body component report `INDEX_NONE`. A synthetic contact that stands for such a hit must set `Item = INDEX_NONE`, or code that matches the struck resource by receiver and item, such as the pierce exclusion `FRpgHarvestResourceId::Matches`, treats the struck node as another resource (HRW-03).
- `FRpgSwingTraceWindow::TraceSampleMotionForTests` sweeps two hand-built tool poses through a standalone world on the real trace channel, so a test can prove which collision a swing reports without an animated mesh. A test ability can override `URpgGameplayAbility_Harvest::PlayToolSwing` to start the swing without a montage and feed the window's hits to it (HRW-03).
- A new object of a native class copies only those class default properties that already differed from its constructor when the class was linked (`CustomPropertyListForPostConstruction`). A test that changes a native test ability's class default at runtime, such as its activation policy, therefore does not reach the instance that `GiveAbility` creates. Input processing reads the class default and the ability reads its instance, so set both (HRW-04).
- `UGameplayAbility::GetCurrentSourceObject` and `GetCurrentAbilitySpecHandle` ensure on a CDO. In an `AbilityActivatedCallbacks` handler, check `IsInstantiated()` first and read the spec from the ASC.

## GameplayEffects in tests

- A test can build an effect without an asset. Create it with `NewObject<UGameplayEffect>(GetTransientPackage())`, set `DurationPolicy` and `DurationMagnitude`, add components with `AddComponent<T>()`, and apply it with `ApplyGameplayEffectToSelf`. `URpgAbilityTuningEffectComponent::MakeTransientEffectForTests` builds one with Ability Tunings (HRW-05a).
- `UGameplayEffect` is `MinimalAPI`, and its `SetStackingType` is editor-only and not exported, so project code cannot link against it. The `StackingType` property has been deprecated since 5.7. Read it with `GetStackingType()`; a test sets the property inside `PRAGMA_DISABLE_DEPRECATION_WARNINGS` (HRW-05a).
- `OngoingTagRequirements` of `UTargetTagRequirementsGameplayEffectComponent` inhibit an effect as soon as it is added. On authority, adding or removing the loose tag flips `bIsInhibited` synchronously. `bIsInhibited` is not replicated; every machine computes it from its own tags.
- Its `ApplicationTagRequirements` also refuse instant effects: `ApplyGameplayEffectSpecToSelf` calls `CanApply` before it splits instant from duration effects, and the returned handle's `WasSuccessfullyApplied()` is false. `SurvivalRpg.AbilitySystem.Attributes.FocusSet.GainIgnoresItsBlockingTag` covers it (HRW-05b).
- A test that changes a native test effect's class default, such as an ignored tag through `FindOrAddComponent<UTargetTagRequirementsGameplayEffectComponent>()` on `GetMutableDefault`, must restore it when it ends; specs read the class default (HRW-05b `FScopedIgnoredFocusTag`).
- Attribute sets granted after the HUD bound (HRW-05b):
  - A set added on the server, by `AddAttributeSetSubobject` or a GameFeature's AddAbilities grant, changes no value. No attribute-change delegate fires on the listen-server host.
  - Clients get one per attribute from the set's first replication: with `REPNOTIFY_Always`, `SetBaseAttributeValueFromReplication` broadcasts even without an aggregator.
  - The player state sends `Event.Abilities.Changed` through the ability system after GameFeature grants. `URpgCharacterStatsViewModel` refreshes on it through `GenericGameplayEventCallbacks`.
- An owner-only set (`COND_OwnerOnly`) still reaches every client as a replicated subobject. Other players' copies read the constructor defaults, such as `MaxFocus` 100, never the owner's values (`SurvivalRpg.Network.HarvestFocusPIE`).
- A range loop over `GetActiveGameplayEffects()` already skips effects pending removal. After a removal or expiry, `GetActiveGameplayEffect(Handle)` returns null.
- A duration effect expires on the world timer manager. Step the timers past the duration as in [Timers in test worlds](#timers-in-test-worlds).
- Every application of an effect shares its components, because the effect asset is their outer. Keep per-application state out of a component.

## GameplayCues and prediction

- A cue the server adds (`AddGameplayCue`) or executes (`ExecuteGameplayCue`) while still inside a client's predicted activation carries that client's prediction key. The owning client assumes it predicted the cue and never plays it, while every other machine does. This covers server code called synchronously from `ActivateAbility` and message handlers that run inside the killer's activation. Wrap the call in `FScopedPredictionWindow(ASC, FPredictionKey(), false)`, as `URpgGameFeatureAction_AwardKillXP` and `URpgGameplayAbility_Harvest` do; the tests `SurvivalRpg.Network.KillXPCuePIE` and `SurvivalRpg.Network.HarvestCuePIE` prove it.
- A test can read the key from `UAbilitySystemComponent::ActiveGameplayCues` by reflection after `InternalTryActivateAbility(Handle, FPredictionKey::CreateNewPredictionKey(ASC))`.
- `GameplayCueFunctionLibrary.ExecuteGameplayCueOnActor` on an actor with an ability system fires only on authority and replicates through the ASC; on a client it does nothing. Actors without an ASC play it locally.
- A looping cue on a replicated actor without an ASC: `AddGameplayCueOnActor` plays locally, so add it in BeginPlay unless a replicated "ended" flag is set, and remove it in the flag's RepNotify and in EndPlay.
- Cue multicasts are unreliable and limited by `net.MaxRPCPerNetUpdate` per actor and net update; the engine default is 2, and `Config/DefaultEngine.ini` sets Lyra's 10. A PIE test that waits only for the cue it expects passes even when another cue of the same frame was dropped, so assert every cue of the frame and search the log for "no more RPCs are allowed this net update".
- `UGameplayCueManager::OnGameplayCueRouted()` (non-shipping) observes routed cues on every PIE machine in one process; dedicated-server worlds route none. `AbilitySystem.DisplayGameplayCues 1` logs every routed cue per machine.

## PIE network tests

- An equipment definition grants its `SlotAbilitySetsToGrant` when `EquipItemInSlot` equips it, as `ED_Tool_Axe` grants `AS_Tool_Axe`. Granting the same set again in a test leaves two specs on one input. `TryActivateAbility` by handle hides that, but a press activates both, and the second `Exclusive_Replaceable` swing cancels the first at once (HRW-04). Use the equipment's own grant and assert that exactly one spec answers the input.
- Held input: call `AbilityInputTagPressed` once on the owning client's ASC; that client's player controller calls `ProcessAbilityInput` every frame until `AbilityInputTagReleased`, so `WhileInputActive` abilities repeat as for a held key (HRW-04 `HarvestSwingPIE`). Count server activations with `AbilityActivatedCallbacks` and cancels with `OnAbilityEnded`, because the command steps of the other machine do not run every frame.
- Real client predictions: give the ability on the server and call `TryActivateAbility` on the owning client. The avatar must be an autonomous actor; a PlayerState is a simulated proxy on clients, and GAS activates nothing on a simulated avatar, so bind the pawn with `InitAbilityActorInfo(PlayerState, PlayerState->GetPawn())` on every machine.
- A FastArray whose replicated array gets re-sorted crashed the server (`FixedShadowIndex > Index`) once a move rotated three or more entries. Disable FastArray delta struct serialization for such a list, as `FRpgInventoryList` does; `SurvivalRpg.Network.InventoryReorderPIE` covers it.
- Late joiners: when presentation depends on whether a machine saw an earlier state, remember on each machine that it saw that state. Comparing replicated timestamps with the GameState server time fails, because a joining client has not synced the server clock when the state arrives.
- Native gameplay tags (`UE_DEFINE_GAMEPLAY_TAG_STATIC`) in the editor module `SurvivalRpgEditor` ensure at load. Editor-module tests use configured tags and set them on the ability in `OnGiveAbility`, because config tags are not loaded when the CDO is built.
- `SurvivalRpgEditor` must list `GameplayMessageRuntime` itself to broadcast messages; public dependencies of `SurvivalRpg` do not propagate linking.
- Running a PIE network test after `SurvivalRpg.Harvesting` in one session crashed at the PIE world-leak check; run those suites separately.
- Rendered PIE shares the GPU with every other process. A game or other editors holding most of the 12 GB GPU dropped the test editor to about 10 fps, and four combat PIE tests timed out on master and on older commits alike, which looked like a regression. At that rate the authority samples a melee attack window only about twice, and its trace chords pass beside the target. Before suspecting a commit, compare per-test frame rates from the `[frame]` counters in `editor.log` with a passing run, check `nvidia-smi`, and rerun with `--null-rhi` as a control. `CombatRemoteMeleePIE` and `CombatImpactCuesPIE` cap each PIE world step at 1/60 s, the rate of a real server, with `FRpgScopedNetworkTestFrameTimeLimit` (`AWorldSettings::MaxUndilatedFrameTime`), so slow frames slow the worlds down instead of taking larger steps. Under GPU load the worlds then step exactly at the cap, which is the stress case these tests guard. A global `-UseFixedTimeStep` also runs the game faster than real time on fast machines; avoid it.
- A timer set during a frame lags a montage started in the same frame. A server RPC activates the ability before the tick groups, so the montage already advances in that frame; the timer starts counting only after the frame's timer tick and fires strictly after its deadline. The melee authority window that opened only from such a schedule opened one or two frames late (at 60 Hz and 1.5x play rate at montage 0.175 instead of 0.13) and missed hits the owner had predicted from its notify. Open montage-timed gameplay on whichever comes first: the montage's own queued notify, a once-per-frame check of the montage position (a looping timer with `bMaxOncePerFrame`, which ticks after movement and animation), or the timer. Accept the notify only while the running montage instance has reached its time, as `FRpgSwingTraceWindow` does for melee attacks and tool swings.
- On the listen server, a remote client's root-motion montage advances with each received move (`UCharacterMovementComponent::TickCharacterPose`; this autonomous tick pose may run several times per frame), so it jumped from 0.117 to 0.167 in one 1/60 s step, and some queued window-start notifies never arrived. Which path dropped them is not confirmed; `a.EnableQueuedAnimEventsOnServer` dispatches after each move only while an anim graph update is pending. Server gameplay must not depend on such a notify alone. A clock timer alone opened the window at 0.179 and missed; read the montage position instead. The server samples the blade once per frame, so one straight trace chord spanned such a jump and passed beside the target (montage 0.133 to 0.195) even with the window open on time. Even without a jump, the Basic Sword's first combo step turns the blade up to about 85 degrees in one 1/60 s frame. Trace between pose samples along the motion instead: `RpgWeaponTraceInterpolation` interpolates each trace point's transform relative to the body as one screw motion and sub-steps it by angle. Measured against the owner's real swing sampled every 4 ms, the tip's real path stayed within 12 cm (p95) of the screw path across a three-frame (50 ms) jump, against 62 cm for one straight chord. Sampling the montage itself at finer times would also need the bone chain, slot blending and retargeting evaluated on the server.
- The standing multiplayer rule in `AGENTS.md` applies to every gameplay change: cover owner, authority, simulated proxy, late join, and corrections, and observe the remote character in a two-player PIE.
